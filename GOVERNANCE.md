# Governance

This project uses lightweight, transparent governance suitable for early-stage public-interest infrastructure work.

## Maintainers

Maintainers are responsible for stewardship of repository quality, documentation integrity, and decision logs.

Current maintainer model:
- Repository owners act as interim maintainers until a broader maintainer group is formed.
- Additional maintainers may be added through documented consensus and public discussion.

Maintainer responsibilities:
- Review and merge contributions
- Enforce contribution and conduct standards
- Ensure governance, privacy, and security docs stay current
- Keep decisions auditable through issues, pull requests, and changelog entries

## Decision-Making

### Day-to-day decisions

- Routine documentation and non-breaking updates are handled through pull request review.
- Maintainers should seek rough consensus and document reasoning in PR threads.

### Significant decisions

Significant decisions include:
- Governance rule changes
- Privacy or security posture changes
- Template structures that affect evaluation comparability

For significant decisions:
1. Open an issue describing context, options, and tradeoffs.
2. Allow time for community comment.
3. Record final decision and rationale in the merged PR.

## Contribution Process

- Follow `CONTRIBUTING.md` for issue and pull request workflow.
- Docs-first contributions are encouraged.
- Contributors should avoid adding jurisdiction-specific legal interpretations as universal guidance.

## Experiment Governance Principles

All experiments described with this project should follow these principles:

1. Approval before launch
Each pilot should have explicit approvals from appropriate program, policy, legal, privacy, and operations stakeholders.

2. Auditability by design
Pilot plans, metric definitions, analysis approach, and decision rules should be documented before launch and archived after completion.

3. Reversibility and safety
Every pilot should define rollback criteria and a responsible decision owner.

4. Equity and accessibility review
Teams should assess potential unequal impact across participant groups and include accessibility checks in pre-launch review.

5. Minimal-risk operational scope
Experiments should start with low-risk changes (for example, language clarity or sequence adjustments) before high-impact workflow changes.

6. Transparency of limits
Results should be reported with clear caveats, uncertainty, and known constraints.
